How a distributed rate limiter works

By Asfak Shahrier

Track System designLevel Case studyStatus GrowingAbout 11 min read

Every API I've built has a line like throttle:60,1 in it, and I always treated it as magic. Then I asked: what if the API runs on 50 servers and gets a million requests a second? A counter on one machine stops working. These notes rebuild a rate limiter that works across many servers, one problem at a time.

Before we start

How this case study is built

Five versions, each fixing what the last one got wrong.

v1A counter inside each app server
v2Limiter in the API gateway, state in Redis
v3Token bucket instead of simple counters
v4Lua script so concurrent requests can't cheat
v5Redis Cluster, replicas, fail-closed, pushed rules
Why this order

This is a smaller system than WhatsApp or YouTube, but it sits in front of everything. If it is slow, every request is slow; if it is down, the whole API may be down. So every decision here is judged by two numbers: under 10 ms, and always available.

Step 1

What the system must do

Functional

  • Identify clients by user ID, IP or API key
  • Apply rules like "100 requests per minute per user"
  • Reject extra requests with 429 and helpful headers

Non-functional

  • Under 10 ms added per request
  • Highly available; eventual consistency is fine
  • 1M requests/second, 100M daily users

Left out on purpose

  • Analytics on rate limit data
  • Keeping the data long term
  • Perfect consistency across all nodes
Why it works this way

"Eventual consistency is fine" is a big relief. If a user sometimes gets 101 requests instead of 100, nothing breaks. That small allowance is what makes a fast, distributed design possible.

Entities and interface

Entities: Rule (the limit, who it applies to, which endpoints), Client (user, IP or API key, plus its usage state), and Request (who, which endpoint, when).

Why it works this way

Real systems layer several rules at once: per user, per IP, per endpoint, and a global limit. When more than one applies, the strictest one wins.

Step 3

Where the limiter lives

BAD

Inside each app server

With 10 servers, each sees only a tenth of a user's traffic. A limit of 100 quietly becomes about 1,000.

GOOD

A separate service

Accurate, but every request pays an extra network hop and the service becomes one more thing that can fail.

GREAT

In the API gateway

Bad traffic is stopped at the front door before it touches any backend. State is shared through Redis. Chosen.

Step 5

The token bucket, step by step

A bucket holds up to 100 tokens and refills 10 tokens per minute. A quiet user can burst 100 requests at once, then settles to about 10 per minute.

Why it works this way

Real users are bursty: open an app, it fires 20 requests at once, then nothing. The token bucket allows that burst while still enforcing a steady long-term rate. Fixed windows punish it unfairly, and leaky buckets slow it down.

Deep dive 1

Two requests, one token

My first version read the bucket, did the math in the gateway, then wrote it back. Under load, that breaks.

BAD

Read, then transaction

MULTI/EXEC makes the write atomic, but the read happened outside it. The race is still there.

GREAT

One Lua script

Read, refill, check and take the token inside a single Lua script. Redis runs a script all at once, so no other request can sneak in between. Chosen.

Bonus

The script also saves a round trip: one call to Redis instead of a read and a write, which helps the 10 ms budget.

Step 6

Saying no politely

When a request is rejected, return immediately. Don't queue it: queues use memory, trigger retries and make latency unpredictable.

Deep dive 2

1M checks per second

One Redis instance does about 100k to 200k operations a second. Each check needs about 2 operations, so one instance handles 50k to 100k checks. For 1M checks a second we need about 10 shards.

Why it works this way

This is consistent hashing again, the same idea from the WhatsApp design. Redis Cluster does it for us with 16,384 hash slots, so the gateway doesn't need any routing logic of its own.

Deep dive 3

What happens when Redis is down?

A hard question with no single right answer. The limiter can't check anything, so it has to pick a default.

FAIL-OPEN

Let everything through

The API stays up. But if Redis went down during a traffic spike, the backend now gets the whole spike with no protection, and may fall over too.

FAIL-CLOSED

Reject everything

The backend is protected, but the API is effectively offline until Redis recovers. Chosen for this social platform, because limiter outages often happen during viral spikes.

Make it rare

Replicas with automatic failover, plus monitoring of Redis health, check latency and rejection rates, keep either choice from mattering often.

Why it works this way

The right answer depends on what's behind the limiter. For a payments API, letting unchecked traffic through could be far worse than a short outage. For an internal dashboard, failing open might be fine. The skill is asking "which failure hurts less here?"

Deep dive 4

Latency, hot keys and changing rules

Keeping it under 10 ms

  • Connection pooling: the biggest win; a new TCP connection can cost 20-50 ms
  • Regional deployment: gateways and Redis close to users
  • One Lua call instead of several round trips

Hot keys

  • Big legit clients: client-side limiting, batching, premium tiers
  • Abusers: auto-block after repeated 429s; DDoS protection (Cloudflare, AWS Shield)
  • Shared IPs (NAT): higher IP limits, rely on user limits

Changing rules without a deploy

  • GOOD Gateways poll a config DB every ~30 s
  • GREAT ZooKeeper (or Redis pub/sub) pushes changes instantly
  • Push is faster, but must handle dropped connections

Reflection

What surprised me

More servers, weaker limits

With counters in each server, adding servers silently multiplies everyone's limit. Scaling up made the limiter worse.

A race in 4 lines of code

Read, calculate, write looks harmless. Only drawing two gateways side by side showed me how both can win the same token.

Redis, again

Pub/sub in WhatsApp, sorted sets in LeetCode, now hashes and Lua scripts. The same tool solved a different problem each time.

Practice

Try it yourself

Think each one through (or explain it to a friend), then open the answer.

Why can't each server just keep its own counter?

Each server sees only part of a user's traffic. With 10 servers behind a load balancer, a limit of 100 per server lets the user make roughly 1,000 requests. The count has to be shared.

With a fixed window of 100/min, how can a client send 200 requests in 2 seconds?

Send 100 at 12:00:59 and 100 at 12:01:00. Each window sees only 100, so both say OK.

A bucket has capacity 100 and refills 10 per minute. The user was idle for an hour. What happens if they send 150 requests at once?

The bucket is full (capacity caps it at 100), so the first 100 pass and the next 50 get 429. After that they get about one request every 6 seconds.

Why does a Lua script fix the race but MULTI/EXEC alone doesn't?

MULTI/EXEC only groups the writes; the read happened before, outside it. A Lua script runs the read, the math and the write as one step on Redis, so no other command can run in between.

Redis is down. Would you fail open or closed for a payments API?

Usually fail closed: unchecked traffic to payments risks abuse and overload, and a short, clear outage is safer. The answer depends on what each failure would cost.

Your whole university shares one public IP and keeps getting 429s. How do you fix it?

Set a higher limit for IP-based rules and rely mainly on per-user limits for logged-in users, so one shared IP doesn't block everyone behind it.
