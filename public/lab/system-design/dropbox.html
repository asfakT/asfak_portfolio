How Dropbox keeps your files in sync

By Asfak Shahrier

Track System designLevel Case studyStatus GrowingAbout 25 min read

I save a file on my laptop, and a few seconds later it is on my phone. I never press "upload" and I never think about it. Behind that small trick is a system that slices files into pieces, fingerprints every piece, and quietly argues with the server about which pieces it already has. These notes rebuild it step by step, from "upload a file" to "keep many devices in agreement".

Before we start

How this case study is built

Five versions, each fixing what the last one couldn't handle.

v1Upload and download through one app server
v2Bytes go straight to S3 with presigned URLs, downloads via a CDN
v3Chunked, resumable uploads with content fingerprints
v4A sync agent: file watcher, push events, polling safety net
v5Faster and safer: delta sync, compression, signed URLs
Why this order

The YouTube note already covered presigned URLs and chunked, resumable multipart uploads, so v2 and v3 will feel familiar. What is new here is sync: the same file lives on several devices, any of them can change it, and they all have to end up agreeing. Fingerprints, delta sync and conflict handling all exist to serve that one goal.

Step 1

What the system must do

Functional

  • Upload a file from any device
  • Download a file from any device
  • Share a file and see files shared with me
  • Sync changes across my devices automatically

Non-functional

  • Availability over consistency
  • Files up to 50 GB
  • Secure, durable, recoverable data
  • Low latency for upload, download and sync

Left out on purpose

  • Editing or previewing files in the browser
  • Per-user storage quotas
  • File version history
  • Virus and malware scanning
Why availability wins

If I upload a file in Germany and my friend in the US sees it a few seconds later, nobody is hurt. Compare that with a bank transfer, where a stale read is a real problem. So the system stays up and accepts writes even if replicas are briefly out of date (eventual consistency).

Step 2

Entities and API

Entities: File (the raw bytes, in blob storage), FileMetadata (name, size, MIME type, owner, status, fingerprint, chunk list) and User. Keeping bytes and metadata apart is the most important split in the whole design.

EndpointSendsReturns
POST /files/presigned-urlFileMetadata (name, size, fingerprint)Upload ID + one presigned URL per chunk
PUT <presigned URL>Raw chunk bytes, straight to S3An ETag for that part
PATCH /files/:fileId/chunksChunk id, status, ETagUpdated chunk status (after the server checks)
GET /files/:fileId/presigned-urlNothingA short-lived download URL
POST /files/:fileId/shareList of usersOK
GET /files/changes?since=<time>Last sync timeChange events: file id, created / updated / deleted, new metadata
Why it works this way

There is no POST /files that carries the file itself. The API only hands out permission slips (presigned URLs) and records metadata, and the bytes go to storage directly. Also, no endpoint takes a userId in the body: who I am comes from my session token, same rule as in the LeetCode note.

Step 3

The full architecture at a glance

The map we're building toward. Two kinds of traffic: small metadata calls through the API, and big byte streams that skip it.

BAD

Files on the app server's disk

One disk fills up, and if the server dies every file dies with it.

GOOD

Upload through the server to S3

Durable and scalable storage, but every byte travels twice, and the file and its metadata can end up out of step.

GREAT

Presigned URL, straight to S3

The server signs a short-lived upload URL, the client sends bytes to S3, and an S3 event marks the file uploaded. Chosen.

Why it works this way

Metadata lives in DynamoDB (PostgreSQL would also be fine; the queries are simple lookups). Downloads follow the same idea as uploads: a presigned download URL is good, but users far from the S3 region are slow, so popular files are served from a CDN close to them. Caching everything at the edge costs money, so only frequently read files go there, with cache headers and invalidation when a file changes or is deleted.

Deep dive 1

Uploading a 50 GB file without tears

One big request fails on every front: 50 GB at 100 Mbps is about 4,000 seconds, Amazon API Gateway rejects bodies over 10 MB, one network blip restarts everything, and the user sees no progress bar.

The fix, which I met in the YouTube note, is to split the file into 5-10 MB chunks on the client and upload them separately with S3 multipart upload. Chunking must happen on the client: if the server does it, the full file still has to travel to the server first. The new question here is: who decides that a chunk is really uploaded?

BAD

One giant POST

Timeouts, the 10 MB gateway cap, and a restart from zero on any drop.

GOOD

Client reports chunk status

Simple, but a buggy or malicious client can mark chunks "uploaded" that never arrived, leaving corrupt files that are hard to debug.

GREAT

Trust, but verify

The client sends each chunk's ETag, and the server confirms with S3's ListParts before updating status. Chosen.

Why it works this way

The chunks array in FileMetadata (each one not-uploaded, uploading or uploaded) is what makes the upload resumable and gives a real progress bar. Verifying with ListParts keeps that array honest, because S3 is the only party that truly knows what it received. Once assembled, the file is a single S3 object again, and HTTP Range requests let a download be resumed or split into parallel pieces too.

Deep dive 2

Fingerprints: naming a file by what's inside

How does the client know "I already started uploading this file yesterday"? Not by its name: I have five files called report.pdf. It needs an identity based on the content.

A fingerprint is a hash of the bytes, for example SHA-256. Same bytes always give the same hash; change one byte and the hash changes completely. The client computes one per chunk and one for the whole file before uploading anything.

Dropbox's own engineering blog shows the real version of this idea. Its client splits files into 4 MB blocks, hashes each with SHA-256, and the ordered list of hashes (the blocklist) is the file. Uploading starts with a commit, not with bytes:

Why it works this way

This gives deduplication for free: if a block already exists anywhere, it is not uploaded twice. The blockserver is just a key-value store from hash to encrypted block and knows nothing about users or files; all meaning lives in the metadata. One caution from the main source: keep the fileId a random UUID and store the fingerprint as a separate field. Two people can upload identical bytes, and they still own two different files.

Deep dive 3

Sync: getting every device to agree

Sync runs in two directions. Local to remote: I changed something, tell the cloud. Remote to local: something changed elsewhere, bring it here. The server is the source of truth.

Remote to localVerdictWhy
Polling onlyGOODEasy to build, but slow to notice changes and wastes requests when nothing changed
WebSocket / SSE onlyGOODInstant, but if a message is lost during a reconnect, the device never learns about it
Push + slow pollGREATReal time when things work, self-healing when they don't. Chosen.

When two devices edit the same file

Say I edit notes.txt on my laptop on a plane, and my phone edits it too while offline. Both reconnect. The main source keeps it simple: last write wins.

Why it works this way

Last write wins is fine for this scope because versioning is left out. A real product would rather not lose data: write the new content as new chunks and move a "current version" pointer, so the old version is still there. The Dropbox desktop app goes further and keeps the losing edit as a separate "conflicted copy" next to the original (that part is from my own use, not the sources). Sync is hard to get right: Dropbox spent about four years rewriting its sync engine (called Nucleus, in Rust) to get stable file IDs and stronger consistency guarantees.

Deep dive 4

Making upload, download and sync fast

The fastest byte is the one you never send. Three tricks: send only what changed, shrink what you send, and send chunks in parallel.

Delta sync means re-uploading only the chunks that changed. It sounds easy with fixed 5 MB chunks, until you insert one byte near the start of a file:

TrickWhat it doesWatch out for
Parallel chunk uploadSeveral parts in flight at once fill the available bandwidthAdapt chunk size to the network
Delta sync (CDC)Only changed chunks travelNeeds content-defined boundaries, not fixed ones
Client-side compressionText shrinks a lot: a 5 GB text file might become about 1 GBSkip images and video; a PNG may shrink only a few percent
CDN for downloadsBytes come from an edge server near the userCosts money; cache only hot files
Why it works this way

Compression happens on the client, so S3 stores the compressed bytes and the backend never sits in the data path. Gzip works everywhere, Brotli squeezes text harder, and Zstandard is fast with good ratios, which makes it a strong client-side pick. Order matters: compress first, then encrypt. Encrypted data looks random, and random data does not compress. Dropbox also found a neat sync speed-up: with streaming sync, a second device starts prefetching blocks while the first is still uploading, which in their tests gave up to 2x faster multi-device sync for large files.

Deep dive 5

Sharing and keeping files private

Two questions: how do I quickly list "files shared with me", and how do I stop a download link from working for strangers?

BAD

Share list inside each file

Finding files shared with me means scanning every file's list. Fine for 100 files, hopeless for billions.

GOOD

Plus a reverse cache

A user → file IDs map makes lookups fast, but now two copies must be kept in sync, ideally in one transaction.

GREAT

SharedFiles table

One row per (userId, fileId), with userId as partition key. One source of truth, one indexed query. Chosen.

Why it works this way

Security comes in layers: HTTPS in transit, S3 server-side encryption at rest (keys stored apart from the data), the SharedFiles table as the access list, and short-lived signed URLs. A signed URL is a bearer token: anyone holding it can use it until it expires. That is why it lives only about five minutes, and why stricter setups also bind it to an IP or require an auth cookie.

Reflection

What surprised me

Upload starts with a question

Dropbox doesn't send bytes first. It sends a list of hashes and asks "which ones do you need?". Deduplication falls out of that for free.

One byte can break everything

I assumed fixed chunks were enough for delta sync. One inserted byte at the top of a file changes every chunk after it.

Push still needs polling

After WhatsApp I thought WebSockets solved freshness. Here a slow poll stays as a backup, because a missed sync event means a stale file forever.

Practice

Try it yourself

Think each one through (or explain it to a friend), then open the answer.

Why not upload files through the File Service?

Every byte would travel twice (client to server, server to S3), the servers would need huge bandwidth, and Amazon API Gateway rejects bodies over 10 MB anyway. Presigned URLs let the client send bytes straight to S3 while the server only signs and records.

My laptop dies at 60% of a 20 GB upload. What happens when it comes back?

The client recomputes the file fingerprint, finds a matching file with status "uploading", reads its chunk list, and uploads only the chunks not marked "uploaded". Then the server completes the multipart upload.

Why does the server call ListParts instead of trusting the client's PATCH?

The client might be buggy or malicious and claim chunks it never sent. S3 is the only party that knows what it received, so the server checks there before marking a chunk uploaded.

Why keep a slow poll if devices already have a WebSocket?

Connections drop, and events sent during a reconnect can be lost. The poll for changes since the last sync time catches anything missed, so every device eventually converges.

Why do fixed-size chunks break delta sync, and what fixes it?

Inserting a byte shifts every later boundary, so every later chunk hashes differently and gets re-uploaded. Content-defined chunking cuts at points chosen by a rolling hash of the content, so boundaries move with the data and only nearby chunks change.

Why compress before encrypting and not after?

Good encryption output looks random, and random data has no patterns to compress. Compressing first shrinks the real content, then encryption protects it.
