How LeetCode runs your code

By Asfak Shahrier

Track System designLevel Case studyStatus GrowingAbout 20 min read

I've clicked "Submit" on online judges thousands of times, from Codeforces rounds to LeetCode contests, and never once thought about what happens next. Somewhere, a stranger's code (mine) runs on someone else's machine, gets checked against hidden tests, and updates a live leaderboard for 100,000 people. These notes rebuild that system one problem at a time.

Before we start

How this case study is built

Five versions, each fixing what the last one couldn't handle.

v1List and show problems from a database
v2Run submitted code on the API server (dangerous!)
v3Run code in locked-down containers
v4Live leaderboard with a Redis sorted set
v5Contest scale: queue + autoscaling workers
Why this order

WhatsApp was about moving messages, YouTube about moving huge files. LeetCode is small by comparison: a few hundred thousand users and a few thousand problems. The hard part is different: it runs code written by strangers. Most decisions in this design are about doing that safely and fast.

Step 1

What the system must do

Functional

  • See a list of problems
  • Open a problem and code in many languages
  • Submit and get feedback quickly
  • Watch a live contest leaderboard

Non-functional

  • Availability over consistency
  • User code is isolated and secure
  • Results within 5 seconds
  • Contests with 100,000 users

Left out on purpose

  • Login, profiles, payments
  • Discussions and social features
  • Analytics
  • Backups and CI/CD
Step 2

Entities and API

Entities: Problem (statement, code stubs, test cases), Submission (code + results), and Leaderboard (rankings for one contest).

EndpointSendsReturns
GET /problems?page=1&limit=100Page numberShort problem list: id, title, level, tags
GET /problems/:id?language=pythonLanguageFull statement + code stub for that language
POST /problems/:id/submitcode, languageA submissionId
GET /check/:submissionIdNothingPending, or the results per test case
GET /leaderboard/:contestId?page=1Page numberRanked users
Why it works this way

The submit body never contains userId or a timestamp. Who you are comes from your login session, and the time comes from the server. Anything the client sends can be faked, and in a contest a faked timestamp would mean a faked rank.

Step 3

The full architecture at a glance

The map we're building toward. Keep it in view: each later section zooms into one part of it.

Why it works this way

Problems are stored in DynamoDB with their test cases nested inside the same document, because the reads are simple: "give me problem 42". The problem list is small enough that a monolith API server would be fine; nothing here needs microservices.

Step 4

What happens when you click Submit

Follow the numbers. The interesting part: the server answers you right away with an ID, and the real result comes later.

Why it works this way

Running code can take seconds, and an HTTP request that waits that long ties up the server. So submission is a long-running task: accept it, give back an ID, do the work in the background, and let the client ask "done yet?". It's the same pattern as video processing in the YouTube design.

Deep dive 1

Running a stranger's code safely

Version 2 ran code directly on the API server. One while(true) or one rm -rf / later, the whole site is down, or worse, someone is mining crypto on our machines.

BAD

Run it on the API server

Data can be destroyed or stolen, CPU gets eaten, and one crash takes down the site for everyone.

GOOD

Virtual machine

Very strong isolation with its own OS, but slow to start and heavy on resources for a 2-second job.

GREAT

Container (Docker)

Starts fast and is reused per language. It shares the host kernel, so it must be locked down carefully. Chosen.

Why not serverless?

AWS Lambda is also a great option: it isolates and scales automatically. But it can have cold starts, which hurt a 5-second target, and it has resource limits. With steady, predictable traffic, a fleet of warm containers is the simpler fit.

Deep dive 2

A live leaderboard for 100,000 people

A contest is 90 minutes and 10 problems. Rank = problems solved, and ties go to whoever finished faster.

BAD

Query the database on every refresh

100k users refreshing every 5 seconds, each one sorting about a million submissions. The database melts.

GOOD

Cache, refreshed every 30 s

Much less load, but the board can be 30 seconds stale, which feels broken in the last minutes of a contest.

GREAT

Redis sorted set

Update the user's score the moment a submission is accepted. Reading the top 1,000 is instant. Chosen.

Why not WebSockets?

WebSockets would push changes instantly, and they were the right call for WhatsApp. Here a 5-second delay is fine and 100k users is modest, so simple polling is enough. A nice touch: poll every 2 seconds in the final minutes and every 10 seconds otherwise.

Deep dive 3

Surviving the contest rush

When a contest starts, submissions spike. A quick estimate shows how much compute that really means.

OptionVerdictWhy
Bigger machines (vertical)BADHits a ceiling, and pays for idle power between contests
Autoscaling containersGREATAdd workers when busy, remove them after (ECS Auto Scaling)
Autoscaling + queueGREATThe queue absorbs the spike and retries if a container dies. Chosen.
Why it works this way

Contests are scheduled, so the rush is predictable. You can also pre-scale: start extra containers a few minutes before the contest begins, instead of waiting for autoscaling to react.

Deep dive 4

One test set, every language

Writing test cases separately for Python, Java and C++ would triple the work and invite mistakes. Instead, tests are written once in a neutral format.

Why it works this way

The hard part is agreeing on serialization: how a tree, a linked list or a graph is written as plain data. Once every harness understands the same format, adding a new language means writing one harness, not rewriting 4,000 problems.

Reflection

What surprised me

"Pending" is a queue

That "Pending..." I've stared at during contests is literally my job waiting in a queue, while my browser asks "done yet?" every second.

Polling won

After WhatsApp, I expected WebSockets everywhere. Here plain polling is the better choice, because a few seconds of delay costs nothing.

The hidden hard part

I thought sandboxing would be the hardest problem. Making one test case work identically in every language turned out to be just as tricky.

Practice

Try it yourself

Think each one through (or explain it to a friend), then open the answer.

Why not run the code on the API server?

User code is untrusted. It could delete or steal data, mine crypto, attack other sites, or simply loop forever and eat the CPU. And if it crashes the server, every user is affected. Isolation in a separate sandbox is required.

A user submits while(true){}. What stops it?

The container's 5-second timeout kills it, and CPU limits stop it from slowing other jobs in the meantime. The submission is marked "Time Limit Exceeded".

Why add a queue if the workers can autoscale anyway?

Autoscaling takes time to react. The queue holds submissions safely during the spike, and if a container crashes mid-run, the job can be retried instead of lost.

Why is a Redis sorted set better than caching the leaderboard every 30 seconds?

The sorted set updates on every accepted submission and keeps itself in order, so reads are both fresh and cheap. A periodic cache is either stale or puts load back on the database.

Why not let the client send its own timestamp with the submission?

Anything the client sends can be changed. A faked earlier time would win tie-breaks. The server records the time itself.

How do you add Rust as a new language?

Build a Rust container image and write one Rust harness that reads the shared test format (arrays for trees, and so on). No existing test cases change.
