How a URL shortener turns long links into short ones

By Asfak Shahrier

Track System designLevel Case studyStatus GrowingAbout 18 min read

I paste short links all the time, in blog posts, in my portfolio, in messages to friends, and I always assumed the service behind them was trivial: store a pair, look it up. It mostly is. The interesting part is doing that one lookup a few hundred thousand times a second, in under 100 ms, without ever handing two links the same code. These notes build it up one problem at a time.

Before we start

How this case study is built

Five versions, each fixing what the last one couldn't handle.

v1One server, one table: save a pair, look it up
v2Unique codes from a counter + base62
v3Fast redirects with an index and a Redis cache
v4Split read and write services, scale each
v5Share one counter across many servers and regions
Why this order

YouTube was about huge files and LeetCode about running strangers' code. A URL shortener is the opposite: tiny rows, simple logic. The whole design comes down to two questions: how do I make a code that is short and never repeats, and how do I answer a flood of reads fast. Everything else follows from the fact that people click links about a thousand times more often than they create them.

Step 1

What the system must do

Functional

  • Give a long URL, get a short URL back
  • Optionally pick a custom alias
  • Optionally set an expiration date
  • Open the short URL and land on the original

Non-functional

  • Every short code is unique
  • Redirects in under 100 ms
  • 99.99% available, availability over consistency
  • 1 billion URLs and 100 million daily users

Left out on purpose

  • Login and account management
  • Click analytics (counts, countries)
  • Spam and malicious URL filtering
  • Real-time analytics consistency
Step 2

Entities and API

Entities: Original URL (the long link), Short URL (the code people share), and User (who created it). In the database this is basically one table keyed by short_code.

EndpointSendsReturns
POST /urlslong_url, optional custom_alias, optional expiration_dateThe short_url, for example short.ly/15ftgG
GET /{short_code}Nothing302 redirect to the long URL, 410 Gone if expired, 404 if unknown
Why it works this way

The redirect is a plain GET on the root path, because the short link has to work when someone simply pastes it into a browser. No JSON, no headers, no client code. The server answers with a status code and a Location header, and the browser does the rest. The 410 vs 404 split (unknown vs expired) is a detail I picked up from the AlgoMaster write-up: it tells the user the link existed once, which is more honest than "never heard of it".

Step 3

The full architecture at a glance

The map we're building toward. Reads go up, writes go down, and each later section zooms into one part.

Why it works this way

A Postgres table with short_code as the primary key is all the storage we need: one row per link, looked up by one key. A background job deletes (or just flags) expired rows. The cache entry for a link gets a TTL (time to live) no longer than the link's own expiry, so an expired link can't hang around in Redis after the database says it's dead.

Step 4

What happens when you shorten a link

Follow the numbers. Most of the time the write service doesn't even talk to Redis, because it already holds a block of IDs.

Why it works this way

Should the same long URL always get the same short code? Most real shorteners say no: two people shortening the same page may want different expiry dates, aliases or stats. So I skip deduplication and let one long URL have many codes. The AlgoMaster write-up adds a useful rule for aliases: keep a reserved word list (admin, api, login) so nobody grabs a path the app itself needs.

Step 5

What happens when you click a short link

This is the path that runs a thousand times more often, so this is where the effort goes.

Why it works this way

302 costs one extra request per click, and that's the point: every click passes through us, so expiry and edits take effect right away. If analytics ever comes back in scope, both extra sources agree on the shape: don't count clicks inside the redirect. AlgoMaster pushes each click event onto a queue like Kafka (the same "do slow work later" idea as the YouTube and LeetCode notes), and the System Design Primer goes even simpler and runs batch MapReduce jobs over the web server logs. Either way the redirect stays fast.

Deep dive 1

Making every short code unique

The code must be short, must never repeat, and should be cheap to make. Three tries.

BAD

Take the URL's first characters

The first 8 characters of most links are www.link or https://. Thousands of URLs share a prefix, so they'd all get the same code.

GOOD

Hash it, keep a slice

Clean up the URL, run SHA-256, base62-encode, keep 8 characters (about 218 trillion options). Works, but slices can collide, so every insert needs a check and a retry with a salt (a few random extra bytes mixed in).

GREAT

Counter + base62

Hand out 1, 2, 3, ... from an atomic counter and write the number in base62. Two links can never get the same number, so there's nothing to check. Chosen.

Why it works this way

Base62 and not base64, because base64's + and / mean things in a URL (a path separator, and a space in query strings). The counter's one weakness is that codes are predictable: anyone can walk 15ftgG, 15ftgH, ... and read other people's links. One fix is to scramble the number with a reversible step (for example, XOR with a secret key) before encoding. For comparison, the System Design Primer's version takes the hash route: MD5 of the user's IP plus a timestamp, base62, first 7 characters, and a database check to regenerate on a clash.

Deep dive 2

Making redirects fast

Without help, finding one code in a billion rows means scanning the whole table. Three layers fix that.

GOOD

Index the code

Make short_code the primary key. Postgres builds a B-tree index for it, so a lookup is O(log n), and the key also enforces uniqueness for free. Still a disk read every time.

GREAT

Redis cache in front

Check Redis first. On a miss, read Postgres and fill the cache. Links almost never change, so invalidation (removing stale entries) is easy. Evict with LRU (least recently used). Chosen.

GREAT

CDN + edge code

Run the redirect at points of presence close to the user (Cloudflare Workers, Lambda@Edge). Popular links never reach our servers. Costs more and is harder to debug.

Why it works this way

Clicks are very uneven: a few links get most of the traffic. AlgoMaster applies the 80/20 rule here and works out that caching the hottest 20% of a day's links in its (smaller) example fits in about 25 MB of memory. Rows are tiny, so even a generous cache is cheap. The CDN layer is the same trick as YouTube's video segments, just with 100-byte answers instead of megabytes.

Deep dive 3

Scaling to 1 billion links

Two quick estimates decide most of this: how much data, and how many requests.

OptionVerdictWhy
One server does everythingBADReads and writes compete, and you can't scale one without the other
Split read and write servicesGREATMany read instances, a few write instances, each behind a load balancer. Chosen.
Database replicas + backupsGOODReplicas take over if the primary dies (and can serve cache misses); backups protect against bad deletes. More to operate.
Sharding from day oneBAD500 GB fits on one machine. Shard (for example with consistent hashing) only when hardware runs out.
Why it works this way

At about 1 write per second, any database works: Postgres, MySQL or DynamoDB. The advice is to pick the one you know, and default to Postgres. For me that's a relief: the same Postgres or MySQL I use with Laravel and Django every day is enough for a billion-link service, as long as the cache takes the reads.

Deep dive 4

One counter, many servers

Once there are several write instances, a counter in each server's memory would hand out the same numbers twice. The counter has to live in one shared place.

Why Redis is safe here

Redis runs commands one at a time on a single thread, so INCR is atomic: two callers at the same moment get 1000 and 1001, never both 1000. One instance handles 100k+ operations a second.

Many regions

Give each region its own range: region A uses 0 to 1 billion, region B uses 1 to 2 billion. Writes hit the local Redis; reads are served everywhere from caches.

When Redis crashes

Sentinel (or Redis Cluster) fails over to a replica. If a few counter values are lost, the result is a gap in the numbers. Gaps are fine: we need unique codes, not continuous ones.

Why it works this way

It's the same idea as the LeetCode leaderboard: let Redis's single-threaded, atomic commands handle the concurrency so my app code doesn't have to. And just like the rate limiter note, the shared state lives in one fast store while the app servers stay stateless. If something still slips through (say a failover hands out a used block), the UNIQUE constraint in Postgres rejects the duplicate instead of silently overwriting a link.

Reflection

What surprised me

The "faster" redirect is wrong

I'd have picked 301 because the browser caches it. That's exactly the problem: once cached, I lose control of the link forever.

It's base conversion

The core trick is converting a number to base 62, something I've done in contest problems a hundred times. I didn't expect it to be the heart of a real product.

Gaps are fine

My first instinct was to protect the counter from losing values. But nobody needs IDs to be continuous, only unique, and that makes failures much cheaper.

Practice

Try it yourself

Think each one through (or explain it to a friend), then open the answer.

Why use 302 instead of 301 for the redirect?

A 301 is cached by the browser, so later clicks skip our server. Then the link can't be expired, edited or counted. A 302 sends every click through us, at the cost of one extra request.

Why not just use the first 8 characters of the long URL?

Huge numbers of URLs start the same way (https://, www., the same domain). They would all get the same code, which breaks the "one code, one URL" rule.

What does the counter approach give up compared to hashing?

Predictability: sequential codes can be guessed and enumerated. It also needs a shared counter. A reversible scramble (like XOR with a secret) before encoding hides the order.

Two write servers ask Redis for the next ID at the same instant. Can they get the same one?

No. Redis executes commands one at a time on a single thread, so INCR / INCRBY are atomic. Each caller gets a different value (or a different block).

Redis crashes and the last few counter values are lost. Is that a problem?

Not really. Skipped values only leave gaps, and gaps are harmless because codes need to be unique, not continuous. If a lagging replica ever hands out a value that was already used, the UNIQUE constraint in Postgres rejects the insert and the server just takes the next ID.

Why must the cache TTL be no longer than the link's expiry?

Otherwise Redis could keep redirecting to a link the database already considers expired. With TTL ≤ expiry, the cache entry disappears on its own in time.
