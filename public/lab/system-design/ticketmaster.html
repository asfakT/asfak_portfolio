How Ticketmaster sells one seat to exactly one person

By Asfak Shahrier

Track System designLevel Case studyStatus GrowingAbout 22 min read

I've wired Stripe checkout into a Laravel ticketing platform before, so the payment half of this problem felt familiar. The other half did not: ten million people pressing "Buy" for the same concert, and every seat must go to exactly one of them. A seat map that lies, or a seat sold twice, is a real person crying outside a stadium. These notes rebuild the system one problem at a time, from a single database transaction to a waiting room.

Before we start

How this case study is built

Five versions, each fixing what the last one couldn't handle.

v1View and book in one Postgres transaction
v2Hold seats during checkout with a Redis lock + TTL
v3Pay with Stripe, confirm by webhook
v4Survive the rush: caching + a virtual waiting queue
v5Fast, typo-friendly search with Elasticsearch
Why this order

WhatsApp was about delivering messages, YouTube about moving huge files, LeetCode about running strangers' code. Ticketmaster is about one scarce thing that many people want at the same moment. So the order follows the money: first make sure a seat can never be sold twice, then make checkout pleasant, and only then worry about the crowd and the search box.

Step 1

What the system must do

Functional

  • View an event, with a seat map showing what's free
  • Search for events
  • Book tickets for an event

Non-functional

  • Availability for viewing and search
  • Consistency for booking: no double booking
  • About 10M users on one popular event
  • Search under 500 ms
  • Read-heavy, around 100 reads per write

Left out on purpose

  • "My tickets" page and admin tools for adding events
  • Dynamic pricing
  • GDPR, backups, CI/CD
  • Fault tolerance and payment security in depth
Step 2

Entities and API

Entities: Event (date, description, type), Venue (address, capacity, seat map), Performer, Ticket (one per seat: section, row, seat, price, status), Booking (user, ticket IDs, total, status) and User.

EndpointSendsReturns

Why it works this way

The first version had a single POST /bookings that took seats and card details together. The flaw: you type your card number, press Pay, and learn the seat was gone all along. Splitting it into reserve then pay means the seat is yours before you reach for your wallet. A Booking exists separately from Ticket because one order can hold four seats that share one payment.

Step 3

The full architecture at a glance

The map we're building toward. Each later section zooms into one corner of it.

Why it works this way

Events, tickets and bookings live in one PostgreSQL database on purpose. They are tightly linked, and "mark these tickets sold and confirm this booking" must happen as one all-or-nothing transaction (that's what ACID gives us). Splitting them across services and databases would turn a single transaction into a distributed headache for no real gain.

Deep dive 1

Holding a seat while someone pays

Checkout takes minutes. During those minutes the seat must look taken to everyone else, and it must come back on its own if the buyer walks away.

BAD

Hold a row lock in Postgres

SELECT ... FOR UPDATE inside a transaction that stays open until payment finishes. Long transactions pile up locks, risk deadlocks, and an abandoned tab can keep a seat locked far too long.

GOOD

Status + expiry + cron job

Mark the ticket RESERVED with a timestamp; a cron job frees expired ones. It works, but seats come back late (only when the job runs), and if the job dies, seats stay stuck.

GREAT

Expiry checked on read

A seat counts as free if it's AVAILABLE, or RESERVED with an expiry in the past. A short transaction claims it for 10 minutes. Correct with no cron, at the cost of slightly heavier queries (a compound index helps).

GREAT

Redis lock with a TTL

SET ticket:id owner NX EX 600. Redis deletes the key itself after 10 minutes. Postgres only needs two states: AVAILABLE and BOOKED. Chosen.

Why it works this way

Postgres has no built-in "delete this row in 10 minutes"; Redis does, and it's fast. For a booking of several seats, take the locks one by one and give back any you got if one fails (a Lua script can do it atomically when the keys sit on the same Redis node). The Redis docs add two habits I'll keep: store a unique random value as the lock's owner, and release with a check-then-delete script so you never delete a lock someone else now holds. They also warn that with async replication, a failover can briefly let two clients hold "the same" lock. That's why the design keeps a safety net: Postgres still guards the final write with OCC (optimistic concurrency: the update only succeeds if the row hasn't changed since you read it), so a seat can't be sold twice even if Redis misbehaves.

Deep dive 2

The checkout flow, step by step

Follow the numbers. The card number never touches our servers, and the booking is only confirmed when Stripe says the money arrived.

Why a token, not a card number

Stripe.js turns card details into a token inside the browser. Our servers only ever see the token, which keeps us out of most PCI compliance work.

Why a webhook

Payment can be slow or need extra checks (like 3-D Secure). Stripe calls us when it's truly done, carrying the bookingId in its metadata.

Why it must be idempotent

Stripe may send the same webhook twice. The handler uses bookingId as an idempotency key and checks the status first, so a repeat does nothing.

What if the lock expires mid-payment?

Say I take 11 minutes to pay and someone else grabs my seat at minute 10. Both payments might go through, but Postgres's OCC lets only one "mark as sold" write win. The loser gets an automatic Stripe refund. Annoying, but no double booking. To make it rarer: choose a generous TTL, and extend the lock the moment payment begins.

Deep dive 3

When millions open the same event page

At 10 a.m. on sale day, everyone loads the same event page. With about 100 reads per write, the read path is where the load lives.

PieceVerdictWhat it does
Read-through cache (Redis or Memcached)GREATOn a miss, read Postgres and fill the cache; later reads never touch the database
Load balancingGREATRound robin or least connections spreads requests across instances
Horizontal scalingGREATThe Event Service keeps no state, so we just add copies behind the balancer
Why it works this way

This is the same "make the service stateless, put a cache in front of the database" move from my YouTube and LeetCode notes. The new wrinkle is two kinds of data with different freshness needs on one page: the venue never moves, but the seat map changes every second. Giving each its own TTL avoids both a stale map and a hammered database.

Deep dive 4

A waiting room for the Taylor Swift problem

Caching keeps the page up. But if 10 million people reach the seat map at once, every seat they click is gone a second later. The system works; the experience doesn't.

GOOD

Live seat map with SSE

Server-Sent Events push "seat 7 taken" to every open map, so nobody clicks a grey seat. Great for normal events; for the biggest ones, seats still vanish faster than you can click.

GREAT

Virtual waiting queue

Put people in line before they see the map, and let them in a batch at a time. The ones inside have a calm, real chance to pick seats. Chosen.

Why it works this way

This is my LeetCode note's queue turned around: there, the queue protected machines from a burst of jobs; here, it protects people from a burst of other people. Updates only flow one way (server to fan), so SSE is enough; WebSockets, which I needed for WhatsApp's two-way chat, would be overkill. Cloudflare's Waiting Room product shows what this looks like for real: you set a target for total active users and new users per minute, the waiting page refreshes every 20 seconds with an estimated wait, and for a scheduled sale you can open a pre-queue and shuffle everyone at the start time, so refreshing at 9:59:59 gives no edge over joining at 9:50.

Deep dive 5

Search that's fast and forgives typos

The first version searched with LIKE '%Taylor%'. A leading wildcard means the database can't use an index and reads every row. Fine for 100 events, hopeless for millions.

GOOD

Indexes + tidy queries

Index name, date, performer and location; use EXPLAIN, LIMIT, no SELECT *. Still weak at partial matches, and every index slows writes.

GREAT

Full-text index in Postgres

tsvector with a GIN index gives real word search inside the database. Costs storage and upkeep, but no new system.

GREAT

Elasticsearch + CDC

A search engine built on inverted indexes, with fuzzy matching for typos. Kept in sync from Postgres by change data capture. Chosen.

Making repeat searches fasterVerdictNotes
Cache results in Redis or MemcachedGOODKey built from every search parameter; TTL like 24 hours for a keyword + date query. Invalidation is tricky, especially with fuzzy results.
Elasticsearch's own caches + a CDNGREATShard-level filter and request caches inside Elasticsearch; CloudFront caches results near users. Only for results that aren't personalized.
Why it works this way

Postgres stays the only place we write; Elasticsearch is a read-only copy built for searching. CDC (change data capture) reads the database's own change log and replays every insert, update and delete into the index, so the app never has to remember to "also update search". The cost is a second cluster to run and a short lag before a new event shows up in search, which is fine because search is on the "availability over consistency" side of our requirements.

Reflection

What surprised me

The best cleanup is none

I expected a background job to free abandoned seats. Letting the lock's TTL do it means there's no job to crash and nothing to forget.

Two locks, on purpose

Redis holds the seat, and Postgres still double-checks with OCC. It felt redundant at first; then I read how a Redis failover can briefly hand out a lock twice.

The queue is about feelings

The waiting room isn't mainly there to save the servers. It's there so the people who get in don't spend ten minutes clicking seats that are already gone.

Practice

Try it yourself

Think each one through (or explain it to a friend), then open the answer.

Why is search allowed to be slightly stale, but booking isn't?

A new event showing up in search a few seconds late hurts nobody. Selling one seat to two people means a refund, an angry fan and a broken promise. So search and viewing favour availability, and booking favours consistency.

Two people click the same seat in the same millisecond. What happens?

Both send SET ticket:id ... NX EX 600 to Redis. Redis runs commands one at a time, so one sets the key and gets OK; the other finds the key already there and gets nil. The loser sees "seat just taken".

Why not keep a SELECT ... FOR UPDATE lock open while the user pays?

Payment takes minutes. A transaction open that long holds locks, piles up contention and risks deadlocks, and an abandoned or crashed session can keep the seat locked. Short transactions plus a TTL lock avoid all of that.

Stripe sends the "payment succeeded" webhook twice. What stops a double update?

The handler is idempotent: it uses bookingId as the key and checks the booking's status first. If it's already confirmed, the second call does nothing.

A fan pays at minute 11, after their 10-minute lock expired and someone else grabbed the seat. Now what?

Only one "mark sold" write can succeed in Postgres thanks to OCC. The other buyer's payment is refunded automatically. Generous TTLs and extending the lock when payment starts make this rare.

Why use change data capture instead of having the app write to both Postgres and Elasticsearch?

Dual writes drift: if one write fails, the two stores disagree. CDC reads Postgres's own change log, so every committed change reaches the index and the app only has one place to write.
