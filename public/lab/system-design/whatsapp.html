How WhatsApp delivers a message

By Asfak Shahrier

Track System designLevel Case studyStatus GrowingAbout 25 min read

I send a message from Dhaka and my friend's phone in another country buzzes in under half a second. If her phone is off, the message still waits for her. I wanted to understand how that works at the scale of billions of people, so I rebuilt the design step by step: start with one server, see where it breaks, fix it, and repeat. These are my notes from that process, with a diagram for every step.

Before we start

How this case study is built

Real systems are not designed in one go. They grow. This note follows the same path: each version solves one new problem the previous version couldn't.

v1One server, two friends online
v2Friend is offline: add an inbox
v3Photos: move bytes to blob storage
v4Billions of users: many servers + pub/sub
v5Real life: many devices, dead sockets, lost messages
Why this order

When I first looked at the final architecture, it was 15 boxes and I couldn't tell why any of them existed. Building it one problem at a time made every box earn its place: if you can't name the problem a box solves, it doesn't belong in the design.

Step 1

Requirements

Functional (in scope)

  • Group chats, up to 100 members
  • Send and receive messages
  • Receive messages sent while offline (up to 30 days)
  • Send and receive media

Non-functional

  • < 500 ms delivery for online users
  • Guaranteed delivery (no lost messages)
  • Billions of users, high throughput
  • Store on server only as long as needed
  • Survive single component failures

Left out on purpose

  • Voice and video calls
  • Business accounts
  • Signup, profiles
  • Spam, scraping, deep security
Why it works this way

"Store only as long as necessary" is the requirement that shapes everything. WhatsApp is not a chat archive like Slack or Discord. The server is a delivery buffer: once every device acks, the message is gone. That is why we get an Inbox table with TTL instead of a giant history store.

Step 2

Core entities and API

Entities: User, Chat (2 to 100 users), Message, Client (one user, many devices). The API is a set of commands over one persistent WebSocket, not REST.

Why it works this way

Why WebSocket? Chat is high-frequency and bidirectional: the server must push to Bob without Bob asking. Polling wastes battery and adds latency; long-polling works but reconnects constantly. WhatsApp itself runs a custom binary protocol over TLS/TCP (derived from XMPP), but a WebSocket captures the same idea and is what most of us would build with today.

Why it works this way

Creating a chat writes the Chat row and up to 100 ChatParticipant rows. A DynamoDB transaction holds up to 100 items, so a 100-member chat sits right at the limit, so it is safer to batch the participant writes for the biggest chats. Also why an L4 balancer: WebSockets are long-lived TCP connections, we don't need L7 routing, and L4 is cheaper per connection.

Step 4

Alice sends Bob a message

Alice and Bob are connected to different chat servers. Follow the numbers top to bottom.

Why it works this way

Notice the server acks Alice (single tick) before Bob gets anything. That decouples sender latency from recipient health. For a group of 50, step 2 writes 1 Message row plus 49 Inbox rows, and step 4 publishes to 49 channels. That fan-out is where your ~40K msg/s turns into ~100K writes/s.

Step 5

Bob comes back online

While Bob was offline, steps 4 to 8 above failed silently. The Inbox kept his messages. On reconnect, Bob pulls them.

Why it works this way

What if Bob never comes back? TTL on Message and Inbox deletes rows after 30 days for free, with no cron job. Delivery is at-least-once here (if the ack is lost, Bob gets the message again), so the client must dedupe by messageId. The short version I keep in my head: "at-least-once delivery, plus a client that ignores repeats."

Step 6

Sending a photo

BAD

Blob in the database

DynamoDB items cap at 400 KB, and chat servers would stream every byte. Expensive and slow.

GOOD

Chat server forwards to S3

Storage is right, but chat servers still carry media bandwidth they don't need.

GREAT

Client uploads directly

Server only signs a URL. Bytes go client → S3 → client. Chat servers stay tiny.

Why it works this way

CDN is optional here: a file is shared to at most 100 people, so the cache hit ratio is low (unlike Instagram). Open problem to mention: deleting media as soon as all recipients downloaded it, rather than waiting 30 days. A reference count per attachment, decremented on each ack, is one answer.

Deep dive 1

Scaling to billions: who is on which server?

200M concurrent sockets ÷ ~1-2M per host = hundreds of chat servers. Alice is on server 1, Bob on server 7. How does server 1 reach Bob?

BAD

Just add servers

The load balancer spreads connections randomly. Server 1 has no idea where Bob lives.

BAD

Kafka topic per user

~50 KB overhead per topic × 1B users ≈ 50 TB of metadata. Kafka is not built for that many topics.

GOOD

Consistent hashing

Route Bob to a fixed server by hash. Works, but rebalancing sockets on scale-up is painful.

Partition channels byGood forCost
User (user:bob)1:1 chats, which are most of WhatsAppA 100-person group = 99 publishes per message

HybridChats above ~25 members use chat channels, small ones use user channelsTwo code paths; solves the "celebrity" fan-out problem
Why it works this way

Redis Pub/Sub is at-most-once: if no one is subscribed, the message evaporates. That is fine, because the Inbox is the durable path. The picture that made it click for me: "Pub/Sub is the doorbell, the Inbox is the mailbox." Added latency is a few milliseconds; one Redis host has been benchmarked handling ~100K updates/s at under 30% CPU.

Deep dives 4 & 5

Ordering and "last seen"

Message order

Don't build a distributed consensus system. Chat servers sync clocks with NTP and stamp each message on receipt. Every client sorts by that server timestamp, so all members see the same order. A message can occasionally land above one sent a moment later, and that is acceptable.

BAD

Last seen: write every heartbeat

200M users × every 10 s = millions of DB writes per second for a field users glance at.

GREAT

Last seen: write on disconnect

Connected means "online" (live from the socket). Only write lastDisconnectTs when the socket closes, with a conditional write so two servers don't race. Also write on connect for robustness if a server crashes.

Beyond the basics

Going further

Questions that came up while I studied this, answered from ByteByteGo's chat system chapter, WhatsApp's engineering talks and the Signal protocol docs.

✓ / ✓✓ / read ticks

  • ✓ sent: server persisted it (step 3)
  • ✓✓ delivered: recipient device acked; server publishes a receipt to the sender's channel
  • Read: client sends a read receipt when the chat is opened. Same pipeline, tiny payload

End-to-end encryption

  • Signal protocol: keys live on devices, server stores only ciphertext
  • Server keeps public key bundles so offline users can still be messaged
  • Groups use "sender keys" so a sender encrypts once, not per member
  • Consequence: no server-side search or content moderation

Message IDs

  • Need uniqueness + rough time order
  • Snowflake-style 64-bit IDs (timestamp | machine | counter)
  • Client also generates a local UUID for dedupe on retry

Why Erlang?

  • WhatsApp runs on Erlang/BEAM: millions of lightweight processes, one per connection
  • Famous for ~2M connections per box and a tiny engineering team
  • A good reminder that the right runtime can matter as much as the architecture

Archive vs relay

  • Slack/Discord keep history forever: Cassandra/ScyllaDB partitioned by (channel, time bucket)
  • WhatsApp deletes after delivery; history lives on the phone, backed up to the user's cloud
  • Decide which one you're building first; it changes the whole storage design

At even bigger scale

  • Multi-region: home region per user, cross-region pub/sub
  • Cell-based architecture to limit blast radius
  • Graceful deploys: draining 1M sockets without a reconnect storm (jittered backoff)

Reflection

What surprised me

The server forgets on purpose

I assumed WhatsApp keeps every message on its servers. It doesn't: once every device confirms, the message is deleted. Forgetting is a feature, and it makes the system simpler.

Losing messages is allowed, in one place

Redis Pub/Sub can drop a message and the design is fine with it, because the inbox already has a safe copy. Speed and safety live in two different paths.

"Good enough" ordering

I expected a clever algorithm for message order. The answer is a server timestamp. Choosing the simple option, and accepting its small flaw, was a lesson in itself.

Practice

Try it yourself

Questions to check your understanding. Think each one through (or explain it to a friend), then open the answer.

Why not just use a Kafka topic per user for routing?

Kafka keeps per-topic and per-partition metadata (~50 KB each). A billion topics is ~50 TB of overhead and controller load Kafka was never built for. Kafka shines with few topics and huge throughput, the opposite shape of this problem.

Redis Pub/Sub can drop messages. Why is that acceptable?

Because it is only the fast path. The message is already durable in the Message and Inbox tables before we publish. If Pub/Sub drops it, the client finds the gap via sequence numbers on the next heartbeat (or reconnect) and syncs from the Inbox.

A chat server crashes with 1.5M users on it. What happens next?

Their sockets drop. Clients reconnect with jittered exponential backoff (avoid a thundering herd) through the L4 LB to any healthy server. That server subscribes to their channels, then reads their Inbox. Nothing is lost because nothing was only in that server's memory. LastSeen may be stale, which we accept.

How do you make sure Bob doesn't see the same message twice?

Delivery is at-least-once (lost ack means redelivery). Every message carries a unique messageId; the client keeps a set of recent IDs and drops duplicates. Idempotent receiver beats trying to guarantee exactly-once over a network.

Group of 100 people, someone sends a message. What happens on the write path?

1 Message row + 99 Inbox rows (×devices, up to 3 each) and up to 99 publishes. That's why groups dominate write volume. Above ~25 members, switch to a chat-level channel so it becomes 1 publish, and consider batching Inbox writes.

Why subscribe to Redis before reading the Inbox on reconnect?

If you read the Inbox first, a message written and published in the gap between the read and the subscribe is missed by both paths until the next sync. Subscribe first, then read; duplicates are fine because the client dedupes.
